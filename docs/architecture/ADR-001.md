# ADR 001 · Aplicación empresarial sin Firebase

Estado: dirección aprobada; implementación incremental pendiente.

## Decisión

`gemailla-master` conserva la aplicación empresarial. `gemailla-next` mantiene el motor regulatorio independiente. React/Vite se conserva; se agrega una API Fastify en TypeScript, PostgreSQL administrado, Cloud Run para API y workers, Cloud Tasks, Cloud Storage privado, Secret Manager y OpenTelemetry. Infraestructura en Terraform. No se crean microservicios por dominio inicialmente.

La dirección de dependencias es presentación → aplicación → dominio; infraestructura implementa puertos. El dominio no importa Firebase, SQL, HTTP ni el SDK de Vertex.

```text
src/                              # React existente; migración gradual
  domain/                         # lógica y puertos existentes reutilizables
  infrastructure/http/            # acceso al nuevo backend
server/
  domain/{tenancy,documents,assessments,actions,usage}/
  application/                    # casos de uso y autorización
  infrastructure/{postgres,oidc,storage,vertex,regulatory,telemetry}/
  transport/http/                 # Fastify, validación, OpenAPI
  workers/                        # escaneo, evaluación, exportación
contracts/openapi.json
migrations/                       # cambios SQL versionados
infra/terraform/
```

Estas carpetas de servidor son el destino propuesto; PR 0 no contiene implementaciones ficticias.

## Identidad y aislamiento

Proveedor OIDC pendiente. Authorization Code + PKCE; validar firma, algoritmo permitido, issuer, audience, exp y claves rotadas mediante biblioteca mantenida. Identidades ligadas por (issuer, subject), nunca por email como identificador confiable. Acceso del navegador con tokens de corta duración en memoria; no persistir tokens en localStorage. Definir renovación y cierre de sesión con el proveedor antes de producción.

La empresa solicitada en la URL no constituye autorización. Verificar membresía en servidor por operación; roles y planes no se aceptan del cliente. Invitaciones expiran, se consumen una vez y se aceptan con identidad y email verificados. La sesión no transporta permisos indefinidos sin comprobar revocación.

Tablas empresariales con company_id NOT NULL, RLS habilitado y forzado; rol de aplicación sin BYPASSRLS ni propiedad de tablas. SET LOCAL del contexto dentro de cada transacción, también en workers. Rol separado para migraciones. FK y unicidad compuestas por company_id cuando sea necesario; una acción no puede apuntar a una evaluación de otra empresa. RLS complementa la autorización de aplicación.

## Documentos y operación

Cuarentena y documentos aprobados en buckets privados separados; permisos de API y escáner distintos. Ruta generada por servidor, URL de carga breve, límites de tamaño/tipo y validación de contenido real. El cliente nunca establece estado clean. Escanear la generación exacta y verificar hash antes de promocionar; denegar descargas y análisis pendientes o rechazados.

Cloud Tasks llama workers con identidad de servicio y audiencia restringida; el payload contiene IDs, no documentos ni permisos. El worker recupera y valida empresa, trabajo y recursos. Patrón outbox transaccional para publicar tareas; consumidores idempotentes con lease, límite de intentos y estado terminal recuperable. Reentrega no equivale a una nueva evaluación.

## IA y motor regulatorio

Reutilizar la lógica del adaptador Vertex y presupuesto tras extraer sus dependencias de Firestore. Reservar cuota atómicamente antes de llamar; registrar consumo conocido, estimado o desconocido sin declarar gratuitas las llamadas ambiguas. Reconciliar reservas caducadas. Reintentos solo transitorios con backoff, jitter y presupuesto de tiempo. Sin cambio silencioso de modelo en evaluaciones regulatorias.

Gemini interpreta evidencia, no decide permisos ni ejecuta instrucciones de documentos. Entradas limitadas, herramientas permitidas y salida validada por esquema. Registrar modelo, versión del prompt, versión de reglas y documentos con hash. Hallazgos requieren cita verificable y revisión humana; no equivalen a una certificación.

La integración regulatoria es un puerto con contrato versionado, autenticación entre servicios, timeouts y fixtures compartidos. El publicador regulatorio existente debe revisarse antes de añadir otro protocolo. No compartir bases ni replicar el motor en master.

## Observabilidad y datos sensibles

Propagar traceparent con validación; generar traceId interno y devolverlo en errores. Trazas API → outbox → worker → Vertex. Logs estructurados sin texto de documentos/prompts por defecto. Métricas agregadas de latencia, errores y saturación; evitar tenant/user como etiquetas de alta cardinalidad. Consumo por empresa se consulta en un ledger persistente autorizado.

Auditoría de negocio separada de logs operativos, con actor, empresa, acción, objeto y fecha, retención definida y escritura restringida. Respaldo/PITR no sustituye auditoría ni garantiza inmutabilidad regulatoria. Región, residencia, retención, RPO/RTO y objetivos de servicio se fijarán antes del piloto.
